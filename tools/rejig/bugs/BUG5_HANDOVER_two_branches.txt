THE HELPER
----------

One function in programming/manage.c, declared in manage.h:

    calcRegister_t findProgramLabel(uint16_t label, const char *caller);

It resolves a local label 00 to 99 or A to l in the running program the way GTO and XEQ resolve it, passes a
label list index through, and turns a lettered register into a global label name. It reports the miss itself
and returns INVALID_VARIABLE, so every caller is the same three lines:

    label = findProgramLabel(label, "In function fnPgmSlv:");
    if(label != INVALID_VARIABLE) {
      currentSolverProgram = label - FIRST_LABEL;
      currentSolverStatus &= ~SOLVER_STATUS_USES_FORMULA;
    }

Callers: fnPgmSlv, fnPgmInt, fnPgmDrv (branch only), fnVarMnu, fn42VarMnu, _checkArgument (SUMn, PRODn) and
_checkiArgument (iSUMn, iPRODn). PGMPLT reaches it through fnPgmSlv, unchanged. fnVarMnu also gained a bounds
test in _isVarMenu, because labelList[label - FIRST_LABEL] read outside the array for any label the list does
not hold, and VARMNU 01 was a SIGSEGV.

The interactive arm of SOLVE, the integral, PLT f and f' takes a lettered local label as well, by adding
FIRST_UC_LOCAL_LABEL to LAST_LOCAL_LABEL to the three range tests. A typed number there is still a register,
which is what TAM writes for those commands, so SOLVE 45 is unchanged.

E3 reads NaN on the base build as well, on both trees, so it is a property of the route or of the build, not
of the patch. It is recorded as a reference reading and is worth a separate look.

produced no line at all; PGMSLV produced one at once. That is the direct evidence that the EQN plotter,
integrator, solver and derivative do not reach the new code. The same probe was not built for the derivative
branch: the helper is called from the same places there, plus fnPgmDrv.
